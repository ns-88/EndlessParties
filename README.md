## 📝 Описание проекта
EndlessParties - простой сервис для организации мероприятий любого уровня: от встреч в верхах до дружеских посиделок у костра

## 🛠 Возможности API

**управление мероприятиями (Events):**

- **GET /events**: получение списка всех событий

  *Параметры фильтрации (Query string):*
    - `Title` (строка, необязательный) — поиск по названию
    - `Description` (строка, необязательный) — поиск по описанию
    - `From` (дата, необязательный) — фильтр по дате и времени начала (включительно)
    - `To` (дата, необязательный) — фильтр по дате и времени завершения (включительно)
    - `SortDirection` (число) — направление сортировки (1 - по возрастанию, 2 - по убыванию)
    - `Page` (число, необязательный) — номер страницы для пагинации (по умолчанию: `1`)
    - `PageSize` (число, необязательный) — количество элементов на странице (по умолчанию: `10`)

- **GET /events/{id}**: получение события по идентификатору
- **POST /events**: создание события
- **POST /events/{id}/book**: создание бронирования
- **PUT /events/{id}**: обновление события
- **DELETE /events/{id}**: удаление события

**управление бронированиями (Bookings):**

- **GET /bookings/{id}**: получение бронирования по идентификатору
- **DELETE /bookings/{id}**: отмена бронирования по идентификатору

**управление пользователями (Auth)**

- **POST /auth/register**: регистрация нового пользователя
 
  *Параметры метода (Body):*
   - `Name` - имя (логин)
   - `Password` - пароль

- **POST /auth/login**: aутентификация пользователя и выдача JWT-токена
 
  *Параметры метода (Body):*
   - `Name` - имя (логин)
   - `Password` - пароль

## 🏛 Архитектура системы
Сервис бронирования построен на основе паттерна CQRS и Clean Architecture. Доменная логика расположена в слое Domain соответствующих доменных сущностей - Event и Booking,
Use Cases находятся в реализации команд и запросов слоя Application. Решение включает в себя следующие микросервисы:

**Events.Api** - сервис обработки запросов и получения данных о событиях:
```bash
База данных сервиса - EndlessParties.Events
Порт HTTP: 5000
Порт HTTPS: 5001
```
**Bookings.Api** - сервис обработки запросов и получения данных о бронированиях:
```bash
База данных сервиса - EndlessParties.Bookings
Порт HTTP: 5100
Порт HTTPS: 5101
```
**Identity.Api** - сервис работы с пользователями, хранения их учетных данных, регистрации и получения JWT-токенов доступа:
```bash
База данных сервиса - EndlessParties.Identity
Порт HTTP: 5200
Порт HTTPS: 5201
```
Каждый микросервис состоит из следующих слоев:
- Api - API приложения, реализованный для сервиса **EndlessParties.Events.Api** на основе контроллеров, а сервиса **EndlessParties.Events.Worker** - потребителей событий из очереди (консьюмеров);
- App - слой бизнес-логики приложения, реализованный на основе команд и запросов CQRS;
- Infrastructure - слой инфраструктуры приложения, содержащий в себе сервисы для доступа к данным (репозитории) и средства для работы с БД (миграции, конфигурацию, DbContext EF Core);
- Domain - слой доменных сущностей и соответствующей им бизнес-логики, содержит также перечисления и список ошибок домена.

Слои Application и Infrastructure не связаны между собой. Слой Application зависит только от абстракций используемых им компонентов (например, репозиториев или шины событий) и содержит только бизнес-логику, инкапсулированную в обработчиках команд и запросов CQRS.
Сборка Infrastructure выполяет функцию подключения необходимых компонентов для Application и не зависит от нее. Сборки слоя API для каждого из сервисов зависят от остальных слоев и подключают их вместе, регистрируя зависимости в контейнере DI и предоставляя настройки из файла конфигурации.

## 🔄 Механизм взаимодействия сервисов
Взаимодействие сервисов **Events.Api** и **Bookings.Api** происходит через очередь событий Kafka.

При создании нового бронирования сервис **Bookings.Api** публикует событие `BookingCreatedEvent` в топик `endless-parties.bookings.created.v1`.
Его получает сервис **Events.Api** и обрабатывает как запрос на резервирование свободного места, производя необходимые проверки - существование события по данному id,
началось ли уже мероприятие и есть ли в нем свободные места. После обработки запроса, сервис публикует событие `SeatsReservedEvent`
в топик `endless-parties.events.seats-reserved.v1`. Сервис **Bookings.Api** получает это событие как запрос на обработку результата резервирования свободных мест,
и в зависимости от успешности резервирования, переводит бронирование в статус `Confirmed` или `Rejected`.

При отмене бронирования сервис **Bookings.Api** публикует событие `BookingCancelledEvent` в топик `endless-parties.bookings.cancelled.v1`.
Его получает сервис **Events.Api** и обрабатывает как запрос на освобождение занятого места, выполняя проверку наличия события по данному id. После обработки запроса,
происходит сохранение данных в БД и завершение взаимодействия.

## 🔐 Безопасность системы
Ролевая модель представлена пользователями с различным уровнем доступа к возможностям сервисов и состоит из двух ролей:
"Admin" - пользователь-администратор - работа с событиями, обновление, удаление и создание, возможность отмены любых бронирований;
"User" - обычный пользователь - создание бронирований и отмена только тех, которые были созданны данным пользователем.

Любые действия с системой, кроме регистрации новых пользователей, возможны только после аутентификации и авторизации.
Инструкция для получения JWT-токена в Swagger:
- получить учетные данные пользователя, произведя регистрацию методом **POST /auth/register**;
- передать методу **POST /auth/login** учетные данные пользователя, сохранить полученный в ответе метода JWT-токен.

Настройка генерации JWT-токена.
В файле конфигурации appsettings.json сервиса **Identity.Api** необходимо указать значения следующих параметров:

- SecretKey - секретный ключ. Используется алгоритм HmacSha256 (HS256), размер в байтах 32 (256 бит), для кодирования в Base64 - 44 символа, для Hex - 64 символа.
  Должен состоять из абсолютно случайного набора байт; слова, пароли или GUID не подходят из-за низкой безопасности;
- Issuer - наименование сервиса, выпустившего ключ;
- Audiences - потребители ключа (аудитория) - массив наименований сервисов, для которых выпускается токен;
- Expires - время действия токена в минутах.

Для генерации ключа в формате Base64 выполните следующую команду в командной строке:
 ```bash
   openssl rand -base64 32
   ```
## Миграции:
 Схема БД создается автоматически при старте приложения в режиме Development (при локальной разработке и тестировании на компьютере разработчика). Для ручного выполнения миграций выполните команду из консоли разработчика соответствующего проекта:

## Тесты:
 Тесты подразделяются на unit и интеграционные тесты и охватывают слой инфраструктуры и слой приложения.
 Интеграционные тесты реализуются библиотекой Testcontainers for .NET и запускаются в контейнерах Docker, используется образ Postgres 16-alpine.
 Docker должен быть установлен на ПК разработчика, также возможен удаленный доступ.
 Для удаленного доступа создайте файл .testcontainers.properties в домашней директории пользователя со строкой следующего вида:
 ```
 docker.host=tcp://host:2375
 ```
 Для запуска только unit тестов выполните:
 ```bash
   dotnet test --filter "Category=Unit"
   ```
 Для запуска только интеграционных тестов выполните:
 ```bash
   dotnet test --filter "Category=Integration"
   ```
 Для запуска тестов всех категорий выполните:
 ```bash
   dotnet test
   ```

## 🚀 Сборка и запуск

### Предварительные требования
- .NET 10 SDK
- IDE (Visual Studio 2026 / JetBrains Rider / VS Code)
- СУБД PostgreSQL актуальной версии

### Запуск
1. Клонируйте репозиторий:
   ```bash
   git clone https://github.com/ns-88/EndlessParties
   ```
2. Перейдите в директорию проекта:
   ```bash
   cd EndlessParties
   ```
3. Восстановите зависимости и соберите проект:
   ```bash
   dotnet build
   ```
4. Создайте пользователя с правами администратора:
  ```bash
   INSERT INTO "users" ("id", "name", "role", "password_salt", "password_hash")
   VALUES ('ede8a835-bd95-445e-98a9-5542fdba5104', 'Admin', 1, 'P4tE8EVQ2zt3jgqM1GDbUw==', '3O5dl/deUHoIpsprPBQBuyISkJBtSZ8gzyyDSTFmhZk=');
   ```
   Пароль: test

5. Произведите настроки сервисов, указывая значения в файла конфигурации appsettings.json каждого.

   **Identity.Api**
   ```bash
   ConnectionStrings:Postgres:Identity - укажите адрес хоста для подключения к БД;
   JwtToken:SecretKey - секретный ключ для шифрования JWT-токена, должен быть одинаковый для всех сервисов;
   JwtToken:Issuer - наименование издателя;
   JwtToken:Audiences - массив потребителей;
   JwtToken:Expires - время жизни в минутах
   ```

   **Events.Api**
   ```bash
   ConnectionStrings:Postgres:Events - укажите адрес хоста для подключения к БД;
   Kafka:Environment - нанименование окружения;
   Kafka:BrokerAddress - адрес брокера;
   Identity:JwtToken:SecretKey - секретный ключ для шифрования JWT-токена;
   Identity:JwtToken:Issuer - наименование издателя;
   Identity:JwtToken:Audience - наименование потребителя
   ```

   **Bookings.Api**
   ```bash
   ConnectionStrings:Postgres:Bookings - укажите адрес хоста для подключения к БД;
   Kafka:Environment - нанименование окружения;
   Kafka:BrokerAddress - адрес брокера;
   Identity:JwtToken:SecretKey - секретный ключ для шифрования JWT-токена;
   Identity:JwtToken:Issuer - наименование издателя;
   Identity:JwtToken:Audience - наименование потребителя
   ```

6. Запустите сервисы следующими командами:
 
   **Events.Api**
   ```bash
   dotnet run --project src\Events\Api\EndlessParties.Events.Api
   ```
   Swagger: http://localhost:5000/index.html

   **Bookings.Api**
   ```bash
   dotnet run --project src\Bookings\Api\EndlessParties.Bookings.Api
   ```
   Swagger: http://localhost:5100/index.html

   **Identity.Api**
   ```bash
   dotnet run --project src\Identity\Api\EndlessParties.Identity.Api
   ```
   Swagger: http://localhost:5200/index.html
